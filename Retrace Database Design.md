# Retrace: Database Design Document

Version 0.1 | Based on system design v0.3 and PRD v0.6 | 21 October 2026 | Draft for review

This document defines every database, schema, table, column, key, and index in Retrace, along with the roles that may touch them. It follows the decisions in the system design: a central control database, one database per tenant, one schema per service inside each tenant database, and one database role per service per tenant.

## 1. How to read this document

- Section 2 lists the conventions that apply to every table, so they are not repeated.
- Section 3 describes the databases, schemas, roles, and the three common tables every service has (jobs, outbox, inbox).
- Section 4 covers the control database. Sections 5 to 8 cover the tenant schemas: core, ingestion, ai, and notifications.
- Section 9 lists every reference that crosses a schema boundary (these are plain ids, with no foreign keys).
- Section 10 covers retention and deletion. Section 11 covers tables for later phases. Section 12 lists open items and corrections needed in the system design.
- Phase notes: tables are built in the phase of the service that owns them (Core in phase 1, Ingestion and AI in phase 2, Notifications in phase 3).

## 2. Conventions

| Topic | Rule |
| --- | --- |
| Primary keys | Every table has id uuid as the primary key, a UUIDv7 generated by the application. Tables with a composite key say so. |
| Standard columns | Every table also has created\_at timestamptz not null default now() and updated\_at timestamptz not null default now(), unless the table is append-only (then updated\_at is omitted and the table says so). These columns are not repeated in the table listings. |
| Time | All timestamps are timestamptz and stored in UTC. Date-only values use date. |
| Names | snake\_case. Table names are plural. Foreign key columns are named after the table they point to, with \_id. |
| Enumerations | Stored as text with a check constraint listing the allowed values, not as database enum types, because check constraints are easier to change in a migration. |
| Flexible data | jsonb for data that varies in shape (plans, scores, claims). Anything filtered or joined on its own is a real column. |
| Foreign keys | Real foreign keys inside a schema. Across schemas there are no foreign keys, only plain uuid columns (see section 9). |
| Users in tenant data | A user is referenced by user\_id (a plain uuid pointing to the control database) plus a display-name snapshot (user\_name) on rows where history matters (comments, approvals, versions, audit log, actions). Reports then still read correctly after a person leaves. |
| Deletion | Tenant data is hard-deleted. Users and memberships are deactivated, not deleted. Deleting an organization drops its database. |
| Secrets | Secret values are stored as ciphertext (bytea) with a nonce and a key\_version that points to the tenant data key. Plain secrets are never stored. |
| Text limits | Free text columns have sensible length limits enforced by the application. Search text uses PostgreSQL full-text search. |
| Demo data | The organization row carries is\_demo. Demo data lives only in a tenant marked as demo, so it never mixes with real tenants. |
| Index names | ix\_table\_columns for ordinary indexes, ux\_table\_columns for unique indexes. |

## 3. Databases, schemas, and roles

### 3.1 Topology

| Database | Owner service | Contents |
| --- | --- | --- |
| control (one) | Core | Users, organizations, memberships, invitations, and the tenant registry |
| tenant\_{org\_id} (one per organization) | All services | Four schemas, one per service: core, ingestion, ai, notifications. A realtime schema is added in a later phase. |

### 3.2 Roles and grants

| Role | Purpose | Permissions |
| --- | --- | --- |
| control\_core | The Core service on the control database | Read and write on all control tables. No other service connects to the control database. |
| {service}\_{org\_id} (one per service per tenant) | A service working inside one tenant | Usage and all privileges on its own schema only. No access to other schemas. The public schema is revoked. |
| migrator | The migration runner only | Owns the schemas and applies migrations. Services never use it at runtime. |
| readonly\_ops (optional) | Support and diagnostics | Select on selected tables, with approval and logging. Never given secret tables. |

Special grants:

- core.audit\_log: the core role gets INSERT and SELECT only, with no UPDATE or DELETE. A trigger also rejects updates and deletes as a second guard.
- Secret tables (ingestion.integration\_secrets and the key columns of ai.model\_settings): only the owning service role can read them, and the contents are ciphertext.
- Each role has its search\_path set to its own schema.

#### audit\_log

Append-only and tamper-evident. No updated\_at. The core role has INSERT and SELECT only.

| Column | Type | Notes |
| --- | --- | --- |
| seq | bigint not null | Gap-free sequence per tenant, unique. Fixes the order of the chain. |
| occurred\_at | timestamptz not null default now() |  |
| actor\_type | text not null | user, service, system |
| actor\_user\_id | uuid null |  |
| actor\_name | text null | Snapshot |
| actor\_role | text null | Role at the time |
| source\_service | text not null | core, ingestion, ai, notifications |
| action | text not null | For example postmortem.approved, integration.connected, member.role\_changed |
| entity\_type | text null |  |
| entity\_id | uuid null |  |
| summary | text not null | One readable line |
| details | jsonb null | Relevant values, never secrets or evidence text |
| request\_id | text null | Trace id from the gateway |
| prev\_hash | bytea not null | The entry\_hash of the previous entry. The first entry uses 32 zero bytes. |
| entry\_hash | bytea not null | SHA-256 over prev\_hash and the canonical form of this entry |

How the chain works:

1. Appending takes a per-tenant advisory lock, reads the last row, assigns seq and prev\_hash, computes entry\_hash, and inserts. The lock keeps the chain linear when two writes happen at once.
2. Other services publish audit.recorded events. Core consumes them and appends them through the same code path, so there is one writer.
3. A verify job recomputes every hash in order and reports the first mismatch. Editing or deleting any row breaks every hash after it.
4. An audit-ready report (later phase) includes the current head hash and the verification result.

## 10. Retention and deletion

| Data | Retention | How it is removed |
| --- | --- | --- |
| Postmortems, versions, comments, approvals | Until the incident is deleted | Incident deletion cascades inside the core schema |
| Evidence items and timeline events | Until the incident is deleted, or until the organization evidence\_retention\_days passes | The incident.deleted event, or the purge job |
| Draft runs, blameless findings, inline edit events | Until the incident is deleted | The incident.deleted event. Usage counters are kept, since they hold no content. |
| Action items and their events | Until the incident is deleted | Cascade in core. Notifications cleans up related reminders and notifications. |
| Audit log | For the life of the tenant, and never edited | Dropped with the tenant database. Entries about a deleted incident stay, because they hold no evidence text. |
| Exports | Until expires\_at | The purge job deletes the Blob file and the row |
| Jobs | 30 days after finishing | Purge job |
| Outbox rows | 7 days after publishing | Purge job |
| Inbox rows | 30 days | Purge job |
| Notifications | 90 days after being read | Purge job |
| Email log | 90 days | Purge job, because it holds email addresses |
| Email tokens | 7 days after expiry | Purge job |
| Refresh tokens | 30 days after expiry or revocation | Purge job |
| Security events | 1 year, configurable | Purge job |
| Users | Kept, deactivated on request. A deletion request replaces email and display name with placeholders in the control database. | Tenant snapshots keep the old name until an Admin runs a scrub (see open items) |
| An entire organization | Until the Admin deletes it | The deletion flow in the system design: mark deleting, stop access, drop the database and roles, remove keys, secrets, and Blob files, remove the registry entry |

Backups: Azure Database for PostgreSQL backs up the whole server, not individual databases. Deleted data therefore remains in server backups until they expire. For per-tenant restore and export, a nightly logical backup of each tenant database to Blob Storage is planned (see open items).

## 12. Summary, performance notes, and open items

### 12.1 Table count

| Location | Tables |
| --- | --- |
| Control database | 14: users, oauth\_accounts, email\_tokens, refresh\_tokens, organizations, memberships, invitations, db\_servers, tenant\_registry, tenant\_service\_roles, tenant\_keys, provisioning\_runs, jwt\_signing\_keys, security\_events |
| core schema | 14 plus 3 common: org\_settings, incidents, incident\_services, incident\_responders, postmortems, postmortem\_versions, comment\_threads, comments, approvals, action\_items, action\_item\_events, exports, analytics\_summaries, audit\_log |
| ingestion schema | 9 plus 3 common: integration\_connections, integration\_secrets, allowlist\_entries, services, service\_links, discovery\_runs, evidence\_items, timeline\_events, timeline\_event\_evidence |
| ai schema | 6 plus 3 common: model\_settings, usage\_counters, draft\_runs, draft\_section\_runs, blameless\_findings, inline\_edit\_events |
| notifications schema | 4 plus 3 common: reminder\_log, notifications, notification\_settings, email\_log |

That is 14 control tables and 45 tables in every tenant database, 59 in total (not counting later phases).

### 12.2 Performance notes

- The busiest tables per tenant are evidence\_items, timeline\_events, and audit\_log. Their indexes lead with incident\_id or time, matching how they are read.
- Search uses a GIN index on postmortems.search\_vector. No other search index is needed in v1.
- Partitioning is not used in v1. If a tenant grows large, audit\_log and evidence\_items are the candidates, partitioned by month.
- Because each tenant has its own database and each service its own role, connection counts grow with tenants times services. Pools stay very small and a pooler sits in front of the server.

### 12.3 Open items and changes needed elsewhere

1. **System design event catalog.** Add an incident.deleted event (published by Core, consumed by Ingestion, AI, and Notifications) so related data is cleaned up.
2. **Per-tenant backups.** Azure backs up the server as a whole. Decide on a nightly logical backup (pg\_dump to Blob Storage) of each tenant database, which also supports tenant export and moving a tenant.
3. **Name scrub.** Decide whether an Admin tool replaces a removed user's name snapshots in tenant data when a deletion request is made.
4. **Embedding dimension.** Fixed when embeddings are enabled, because the vector column needs one size.
5. **Document size limits.** Set a maximum size for postmortem content (for example 2 MB of JSON) and a limit on manual versions, since each version is a full snapshot.
6. **Citation storage.** Citations live inside the ProseMirror JSON as nodes that carry timeline event ids. If citation queries are needed (for example, which postmortems cite a given event), a derived citations table can be added later.
7. **Graphviz.** The next deliverable is Graphviz code in six diagrams: the control database, the core schema, the ingestion schema, the ai schema, the notifications schema, and an overview of how services reference each other by id.
